# 搜索栏「应用推荐」卡片 —— 根因复核（2026-09-18）

> **1.6.1 结论更新（实测坐实 + 已落地解法）**
>
> 1.6.0 诊断版实测读数：
> ```
> 【诊断】sugPageUse=2                          → isNativeSugPage() 为假
> 【诊断】sugUrl=https://sug.browser.miui.com/
> 【诊断】SearchSugManager.querySug()
> 【诊断】queryKeyword -> {"query":"a", …, "isSearchCard":false, …}
> 【诊断】initRecentAppList: list=0 ad=0 optional=0
> ```
> `BaseSuggestionView#onUpdate` / `SearchSuggestionManager#querySuggest` 一次都没被调用 →
> **卡片 100% 由 `sug.browser.miui.com` 这个远端页面自己渲染**。
>
> 解法（1.6.1）：反汇编 `SearchSugManager` 拿到现成通道 ——
> `.field mWebView:Lmiui/browser/webview/BrowserWebView;`（private instance）+
> `evaluateSugJS(String) = mWebView.evaluateJavascript(js, null)`。
> 于是反射取 `mWebView` 存档，每次 `querySug` / `queryKeyword` 之后向页面注入脚本，
> 隐藏带「广告」标的应用卡片（只 `display:none`、不删 DOM，`MutationObserver` 兜住异步渲染）。
> 详见 `HookBrowser/CHANGELOG.md` 1.6.1 段。

## 触发点

用户实测**原版 base.apk 也拦不住**搜索栏那三张带「安装」按钮的卡片。
这条否掉了 1.5.2 的前提（「原版有可用的搜索广告拦截点，照搬即可」），所以回宿主 20.27 重查。

## 结论（先看这个）

**那三张卡片不在任何 Java 侧列表里，模块层没有可拦的东西。**

两个可能的面，逐条查完后都排除：

| 面 | 结论 | 证据 |
|---|---|---|
| 搜索首页的**原生卡片** `app_recommend` | 是 `RecentAppViewImpl`，但渲染不出「安装」按钮 | `SearchCardFactory#createSearchCard("app_recommend")` → `RecentAppViewImpl`（classes.dex）；`RecentAppViewHolder#bindData` 只做 `getApplicationInfo(pkg,8192)`→图标 + `getAppName()` + 编辑模式，**没有任何按钮**；布局 `res/layout/item_recent_app.xml` 只有 `item_recent_app_icon / _name / _delete` 三个 id |
| 搜索框下拉的**建议页** | 是 WebView（H5），内容远端下发 | `SearchSugManager#initViews` → `ISearchModuleDelegate#createWebView` + `SearchModuleKVPrefs#getSugUrl()` 加载；`SearchSugManager#querySug` 只往网页里塞 `{query, searchid, isSearchCard, secondSearchEnable}`；`SearchSuggestionManager#isNativeSugPage()` = `getSugPageUse()==1`，而 `SearchModuleKVPrefs#getSugPageUse()` 的兜底返回值是 **2**（= 非 native）；`SearchSugManager$initSugWebView$1$1#shouldInterceptRequest` 只拦 QSB 图标前缀（返回本地 Bitmap），**不拦数据请求** |

## 被否掉的假设（连同理由）

| 假设 | 否掉的理由 |
|---|---|
| `SugCardData#a` 是搜索广告总闸（1.5.2 的主拦点） | 反汇编 `lambda$updateSugCardData$0()`，它只写 4 个 KvPrefs key，**没有一个是广告开关**：`pref_show_sug_switch_view`(=`display`)、`pref_sug_expid`(=`expId`)、`pref_second_search_sug`(=`queryRecommend`)、`pref_show_sug`(**只在 `display==true` 时被写成 false**)。且 `pref_show_sug` 的唯一写入方是 `KvPrefs.Qb(Z)`，只会写 false → `KvPrefs.g6()` 恒 false → 传给 H5 的 `isSearchCard` 恒 false，**而卡片照样出来** |
| `RecentAppManager` 展示层过滤能删掉广告（1.5.1 的 ②③） | 全量 LSPosed 日志里**从未出现** `已从应用建议列表移除 N 条广告`（8 个日志文件、多轮真机），说明 `mRecentAdAppList`/`mRecentAppList` 里根本没有 `isAd()==true` 的项 —— 卡片不是从这条链出来的 |
| `SearchBasicVersionData#getAdParem` / `ne.y#{b,e,h}`（1.5.0） | 前者只返回两个个性化参数；后者是设备公共参数注入。日志里 `已把请求参数 isAdvertisingEnabled 改写为 false` 有打过，但没影响卡片 |
| 用 `KvPrefs.g6()`(=`pref_show_sug`) 当杠杆 | 见上，它恒为 false，卡片仍出 → 不是这个开关在管卡片 |

## 顺带纠正的两条旧判断

1. **`SugCardData#a` 的短路不是「去广告」，语义上更接近「不刷新卡片配置」**。
   `SearchCardProvider#updateSearchCardConfig` 走的是 `SearchCardVersionData` 这条**本地版本化数据**
   链路，和 `SugCardData#a` 写的几个 KvPrefs 不是一回事。所以 1.5.2 的「主拦点」既不拦广告，
   也不能算是有效拦截，只是**无害的冗余**（保留或删除都不影响卡片的出现）。
2. **`RecentAppViewHolder` 用 `MATCH_UNINSTALLED_PACKAGES(8192)` 查包**，所以未安装的应用也能拿到
   图标 —— 但它仍然不是截图里那三张卡（没有安装/下载按钮、没有「广告」角标）。

## 结局：A/B 两条路都走完了（2026-09-18 晚）

### A 路径：证实是 H5（1.6.0 诊断版）

```
【诊断】sugPageUse=2                          → isNativeSugPage() 为假
【诊断】sugUrl=https://sug.browser.miui.com/
【诊断】SearchSugManager.querySug()
【诊断】queryKeyword -> {"query":"a","searchid":"…","isSearchCard":false,"secondSearchEnable":false}
【诊断】initRecentAppList: list=0 ad=0 optional=0
```
`BaseSuggestionView#onUpdate`、`SearchSuggestionManager#querySuggest` **一次都没被调用**
→ 卡片 100% 由远端页面渲染，Java 侧无列表。B 路径成为唯一选择。

### B 路径：注入 JS（1.6.1 → 1.6.2）

注入通道（现成的，宿主自己就在用）：

```
.field  mWebView:Lmiui/browser/webview/BrowserWebView;                      ← private instance
.method evaluateSugJS(String js) { mWebView.evaluateJavascript(js, null); }
```

页面真实 DOM 结构（页面身份由 `【诊断】H5 请求` 清单确认，结构由注入回传的命中路径拿到）：

```
#app.flex > .sug-search > div > .topclick-wrap.card-list.card-list_line
  > .card.debug > ul.card__bd.card__bd_top-common.card__bd_topclick
     > li.top-click.debug.top-click_square            ← 广告卡（每张一个 li）
        > a.top-click__sug.card > .top-click__info.flex.flex-v
           > .top-click__subtitle > .second-title > span.ads-tag   ← 「广告」小标
     > li.top-click …                                  ← 正常联想项（同结构、无 ads-tag）
```

**1.6.1 事故**：定位规则写成「从标记往上找最近一个高度 ≥40px 的祖先」。祖先被隐藏后高度归零，
`MutationObserver` 下一轮继续上爬，级联到 `#app.flex` → **整页隐藏，广告和搜索联想一起消失**。
真机日志里 `hidden` 从 1→2、hits 从 `SPAN.ads-tag` → `UL.card__bd` → `DIV#app.flex` 完整记录了这个过程。

**1.6.2 修法**：`closest('a.top-click__sug')` → 外层 `li.top-click`，按结构类名定位；
加四道护栏（根容器黑名单 `html/body/#app`、列表容器黑名单 `card-list/card__bd/topclick-wrap/sug-search`、
高度不得超视口 60%、`data-hb-hidden` 幂等标记）；定位不到就一条不动。

**教训**：WebView 注入里，「元素高度」是**会被自己隐藏动作改变的变量**，不能当定位判据。
定位要用结构（tag + class + 层级），护栏要含幂等标记 —— 否则「判据随副作用变化 + 反复执行」必然级联失控。
回归测试见 `HookBrowser/tools/test_js_filter.js`（mock 的高度会随 `display:none` 归零/塌缩，能复现级联）。

**回归**：`node HookBrowser/tools/test_js_filter.js`（场景 A/B/C）必过；反向回归用 1.6.3 那份旧 JS

## 1.6.5：为什么「一闪而过」，以及怎么做到首帧就不出现

20:48 会话日志（`modules_2026-09-18T20_38_36.log`）把时序钉死了：

```
20:48:37.396  sugCardApi 请求发出
20:48:38.629  卡片图片开始下载（t1.a.market.xiaomi.com/thumbnail/...） ← 卡片已上屏，用户看得见
20:48:38.651  第一次 apply 完成 hidden=2                              ← 卡片可见约 1.25s 才被藏
20:48:39.182  btn=1（按钮判据补掉第三张）
```

两个原因叠加：
1. 注入只发 3 次（0/500/1600ms），页面数据回来后卡片已经画完了才轮到我们；
2. `MutationObserver` 回调里压了 `setTimeout(...,150)` 防抖 —— 每次 DOM 变更都白等 150ms。

**修法一 · CSS 规则前置（主力）**：注入时先往页面塞
`li.top-click:has(.ads-tag){display:none!important}` 这类规则。CSS 一旦进 DOM 就同帧生效，
之后 Vue 渲染出来的卡片在**首次绘制前**就被挡掉，**完全不经过 JS 回调** → 不闪。
选择器只用结构确定的那几个（`.ads-tag` 系列真机确认广告卡独有），
外加按命名规律猜的 `top-click__btn/_install/_download`（猜不中等于没写，不会误杀）。
用 `CSS.supports('selector(li:has(span))')` 判 `:has()`，不支持则整条规则自动失效、退化到 JS。

**修法二 · observer 回调同步化**：去掉 debounce。
`MutationObserver` 回调跑在 microtask 队列，浏览器在**本帧绘制前**清空 microtask，
所以回调里同步改 style 同样赶得上首次绘制。

**修法三**：注入次数 `0/500/1600` → `0/120/320/700/1400/2600`（前密后疏），
并在 `initSugWebView` 之后额外试注一次（页面还没 loadUrl，多半落空，但一旦成立就是最早时机）。

**判读**：返回串新增 `css`（1=CSS 规则已进 DOM）与 `ob`（observer 已注册）。
`css=0` 说明该 WebView 的 Chromium 不支持 `:has()`，只能靠同步 observer，可能出现极短闪现。

**回归**：`tools/test_js_filter.js` 场景 D 断言 —— `<style id="hb-css">` 真插进了 DOM、
规则含 `:has()` 与 `!important`、**observer 回调返回时新增卡片已是 `display:none`**（钉死「不许 debounce」）、
同批插入的正常卡不被误杀、不支持 `:has()` 时不崩且 JS 兜底仍生效。
反向回归：把当前 JS patch 回「无 CSS + 150ms debounce」再跑同套断言 → 退出码 1。

## 1.6.6：卡片藏完之后，残留的空壳容器也要一起塌掉

1.6.5 把卡片做到「首次绘制前隐藏」之后，用户实测残留变成两种形态（其实是同一处）：
**偶尔一行小字「查看更多」，或者一条细长空白**。

原因：我们只 `display:none` 了 `li.top-click`，外层还留着
`DIV.topclick-wrap.card-list > DIV.card.debug > UL.card__bd` —— 这三层各自的 padding / 边框，
以及挂在 `div.card` 里的那行「查看更多」，卡片一没就露出来。

**修法 `collapse()`**：容器内 ≥1 张 `li.top-click` 且全部处于「将被隐藏」状态
（已有 `data-hb-hidden`、命中广告标、或命中安装按钮）→ 塌缩该容器；容器里一旦重新出现
可见卡片 → **立即撤销（复活）**，联想词不会跟着消失。三道边界：
① 只认 `ul.card__bd` / `.card-list` / `.topclick-wrap` / class 含 `card` 的中间层；
② 上溯 ≤3 层，遇 `html`/`body`/`#app`/`.sug-search` 停手；③ **容器内必须有卡**才塌缩
（否则列表还没渲染就会被整层藏掉）。

新增读数：`fold`（塌缩容器数）、`more`（「查看更多」类入口的路径 + 最终可见性 `v=0/1`）。

**回归**：`tools/test_js_filter.js` 场景 E —— ul 内全是广告卡时断言
`fold≥1` + 三层容器全塌缩 + 「查看更多」随父容器不可见（`more` 里 `v=0`）+
`body`/`#app`/`.sug-search` 一个都不许动 + 插入正常卡后立刻复活（`fold=0`、容器恢复、
`data-hb-empty` 清掉）+ 反复执行不抖动不级联。
反向回归：把当前 JS patch 成「不塌缩 + CSS 少一条规则」跑同套断言 → 退出码 1。

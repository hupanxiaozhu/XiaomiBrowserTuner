# 「解锁隐藏设置项」无效 —— 根因定案与修法

> 结论一句话：**不是那条 hook 的问题，是宿主进程读不出模块的 SharedPreferences**
> → 所有开关都退回默认值 → 默认 `true` 的（广告类）照常生效、看起来「正常」，
> 默认 `false` 的（`misc_unlock_pref` / `misc_debug` / `misc_security`）**永远开不起来**。

## 1. 证据（1.6.5 链路自检，`modules_2026-09-18T20_38_36`，20:59 会话）

```
模块注入 com.android.browser（classLoader=dalvik.system.PathClassLoader[…/com.android.browser/base.apk]）
【诊断】开关文件 /data/misc/apexdata/7c4487e0-7bf1-49c1-9acf-5fde5ed3da17/prefs/com.hupan.hookbrowser/settings.xml 存在=true 字节=647
【诊断】文件里的开关：[]
【诊断】默认关的开关现值：misc_unlock_pref=false misc_debug=false misc_security=false
…
已挂载 androidx.preference.Preference#isVisible（1 个重载）
【诊断】宿主在读 Preference#isVisible：开关=关（保持宿主原样…）
【诊断】isVisible 评估到 key=pref_header_desktop_search 宿主原本=false（开关=关）
【诊断】isVisible 评估到 key=pref_incentive_task_center 宿主原本=false（开关=关）
【诊断】采样满 12 个：共评估 12 个 Preference，其中 2 个宿主原本判不可见
```

三行关键读数：

| 行 | 含义 |
|---|---|
| `存在=true 字节=647` | 文件确实在、确实有内容（约 10 个 key 的量级） |
| `文件里的开关：[]` | **可 `XSharedPreferences` 读不出任何 key** → 全部回退默认值 |
| `其中 2 个宿主原本判不可见` | 宿主**确实在用 `isVisible` 藏东西**（`M=2`），所以「开开关就该出来」这个预期成立 |

之前的怀疑（「你是不是没开开关」「宿主没在用 `isVisible`」）到此全部排除。

## 2. 为什么读不出来

两个因素叠加，都在**框架层**，与 hook 逻辑无关：

1. **路径重定向**：模块 Manifest 声明了 `xposedsharedprefs=true`（1.6.0 就加了），
   LSPosed 会把模块的 SP 搬到 `/data/misc/<一级>/<二级>/prefs/<模块包名>/settings.xml`。
   本体在**模块进程**；**宿主进程**要读到它，靠的是 LSPosed 在宿主进程里做的路径重定向。
2. **`XSharedPreferences` 是异步加载的**：`getFile()` 立刻返回路径（所以 `exists`/`length` 都是对的），
   但 `all` / `getBoolean()` 在后台加载完成前返回**空表 / 默认值**。
   `attach()` 里紧接着做的自检与读取，正好落在这个窗口里。

于是出现「stat 得到文件、读不到内容」这种看起来矛盾的现象。

## 3. 修法（1.6.6）

**宿主侧自己读文件、自己解析 XML**，不再依赖框架的加载时机：

- `Config.candidateFiles()` 枚举所有可能路径：
  `XSharedPreferences.getFile()` 报的路径 → `/data/user_de/0/<pkg>/shared_prefs/settings.xml`
  → `/data/data/<pkg>/shared_prefs/settings.xml` → 逐层扫 `/data/misc/*/*/prefs/<pkg>/settings.xml`。
- `Config.loadFromFile()` 逐个 `readText()`，用三条正则解出 `<boolean>` / `<string>` / `<int|long|float>`。
- `Config.raw(key)`：**直读结果优先**，`XSharedPreferences` 只作兜底。
- 保留 1s 缓存（宿主启动阶段 hook 高频触发），改完开关约 1 秒生效，不用重启宿主。

解析用正则而不是 `XmlPullParser`：SharedPreferences 写出的 XML 格式固定，
正则可离线验证（已用 Python 等价实现跑过 boolean / string / int 样例），
且不引入 Android 平台 API 依赖。

## 4. 下次怎么判读

| 日志 | 结论 |
|---|---|
| `【诊断】生效来源=…/settings.xml，共 N 个开关：[…]` | **读到了**（`N>0`）。开开关立刻有效 |
| 每个候选行 `读取=ok(…)` 但 `解出=[]` | 读到了文件但格式不符 → 把 `读取=ok` 那行的头部内容发出来 |
| 所有候选行 `读取=失败` | 宿主进程没权限读该文件 → 走下面的后手通道 |
| `【诊断】500ms 后 XSharedPreferences 读数=[…]` | 若只有它是空、直读正常 → 就是框架异步加载时序（已被直读绕过） |
| `【诊断】宿主在读 Preference#isVisible：开关=开` | 开关生效，隐藏项应立刻出现（约 1 秒延迟） |

## 5. 后手通道（若直读也失败才需要）

按代价从低到高：

1. **模块侧主动回写**：模块进程监听自己的 SP 变化，把值写进一个宿主进程能读的位置
   （例如模块自己的 `ContentProvider`，宿主进程通过注入代码直接查询）。
2. **`ContentProvider` 通道**：模块声明一个 `exported=true` 的 provider（或带自定义权限），
   宿主进程里 `contentResolver.query()` 拿配置。跨进程、同步、不依赖框架 prefs 机制。
3. **共享文件**：模块写到宿主可读的公共目录 —— Android 10+ 基本走不通（分区存储），
   仅在双方都有存储权限时才可行，不推荐。

（1.6.6 还没实现这些 —— 先用日志确认直读通道到底通不通。）

## 6. 定案（1.6.7）：是**文件权限**，且必须在模块进程修

1.6.6 装到手机上以后，自检一次命中（`modules_2026-09-18T20_38_36`，21:09 / 21:10 两次会话同构）：

```
【诊断】开关文件候选 3 个：
【诊断】  /data/misc/apexdata/7c4487e0-…/prefs/com.hupan.hookbrowser/settings.xml 存在=true 字节=647 读取=失败 解出=-
【诊断】  /data/user_de/0/com.hupan.hookbrowser/shared_prefs/settings.xml 存在=false 字节=0 读取=失败 解出=-
【诊断】  /data/data/com.hupan.hookbrowser/shared_prefs/settings.xml 存在=false 字节=0 读取=失败 解出=-
【诊断】生效来源=无（全部走默认值），共 0 个开关：[]
【诊断】500ms 后 XSharedPreferences 读数=[]（对照上面的直读结果）
```

**路径是对的，文件也在，647 字节**（= 十个开关 + `ua_mode` 的完整 XML），但宿主进程 `readText()`
抛异常 —— 连 500ms 后的 `XSharedPreferences` 也是空表。这不是路径问题、不是异步时序问题、
更不是 hook 问题：**`open()` 被拒 = 文件对 other 没有读权限**。

机制（两条叠加）：

| 事实 | 后果 |
|---|---|
| `SharedPreferencesImpl.writeToFile()` 每次落盘都用 `FileUtils.setPermissions(..., 0660, -1, -1)` 把权限重置为 **owner+group 读写** | 模块进程只要写过一次 SP，文件就是 0660 |
| Manifest 的 `xposedsharedprefs` 只让 LSPosed 把文件放到 `/data/misc/apexdata/...`（这个目录别的 app 进得来，所以 `stat` 成功、`exists()=true`） | 「进得来」≠「读得到」—— 目录可进入只保证 `stat`/`length()` 成功 |

`stat` 成功 + `open` 失败，正是我们看到的组合。

**修法（1.6.7）**：权限只能在**文件 owner**（=模块自己的进程）那边改，所以新增
`PrefsFileAccess`，在模块进程里：

1. 反射 `SharedPreferencesImpl.mFile` 拿到重定向后的真实路径（LSPosed 的 prefs 重定向就改在这个字段）；
   拿不到就退到已知根目录 `/data/misc/apexdata/<uuid>/prefs/<pkg>/` 与逐层枚举；
2. 对**所有**定位到的候选文件 `setReadable(true, ownerOnly=false)`（= `chmod o+r`），
   并逐级放行父目录的 `x`/`r`（`/data/misc/apexdata` → `<uuid>` → `prefs` → `<pkg>`）；
3. 触发点两处：**设置页 `onResume`**（打开就修一次）+ **每次 SP 变更后延迟 400ms**
   —— 因为写入会把权限重置回 0660，不重修就会「改一次开关又失效」。

**判读（1.6.7 的宿主侧日志）**：候选行新增 `模式=` （`Os.stat` 取权限位）与异常类型。
- `模式=0660` + `读取=失败 … Permission denied` → 权限问题（回到模块设置页打开一次即可）；
- `模式=0664/0666` 却仍 `读取=失败` → **SELinux** 在挡，chmod 也救不了 → 走上面第 5 节的
  `ContentProvider` 后手（跨进程 binder，完全绕开文件）。

**为什么原版 base.apk 看不出这个问题**：它**没有开关**，`Preference#isVisible` 无条件
`setResult(Boolean(true))` —— 不需要读任何配置，所以「装上即生效」。本工程按「默认值必须保守」
把这几个开关做成默认 false，于是把「读不到配置」这件事暴露出来了。两版 hook 挂在同一个点上，
差别只在开关这一层。
